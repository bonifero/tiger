## 3. Полное выполнение лабораторной

Пройдены пример и все пять вариантов: ввод условия → этапы N…1 → таблицы кандидатов → максимумы и x* → ручное восстановление y/x → итог. Проверены **все 10 оптимальных планов** этих шести задач, включая равные альтернативы. На промежуточных шагах специально выбирается последний из равных максимумов.

| Задача | Максимум | Все проверенные оптимальные планы x | Расход |
|---|---:|---|---|
| Пример: инвестиции | 40 | (0,1,1,2), (1,1,0,2), (1,1,1,1) | 4 из 4 |
| 1: контейнеры | 21 | (2,0,1), (2,2,0), (3,1,0) | 4 из 4 |
| 2: строительство | 34 | (1,0,0,1) | 3 из 3 |
| 3: обувь, выбранная трактовка | 3400 | (1,2) | 5 из 6 |
| 4: перевозка | 2500 | (5,0,0) | 5 из 5 |
| 5: книги, нормированная модель | 320 | (2,0,1) | 4 из 4 |

Полученные протоколы сохранены в [protocols/](protocols/). Дополнительно пройдены свои задачи: B=1, B=200, недоступный по весу груз, нулевой лимит, нелинейные убывающие ценности и дроби. Восстановление допускает оптимум с незаполненной ёмкостью.

Для примера сверены контрольные таблицы из методички: f₄=(35,26,19,9,0), f₃=(37,29,19,10,0), f₂=(40,30,21,11,0); последняя строка кандидатов (40,40,38,36,36).

### Неоднозначности методички

- Вариант 3: фраза «до 2 пар обуви одного из 2-х видов» трактуется как максимум 2 пары каждого вида. При таком ограничении ответ 3400. Если требуется суммарно не более двух пар или производство только одного вида, модель и ответ будут другими. Уточнение присутствует в описании варианта; без согласования нельзя заявлять единственную трактовку.
- Вариант 5: запас указан как 4000 листов, расходы как 1/2/2 листа, количества в таблице лишь 0–3. Приложение явно использует нормированное B=4. Буквальное B=4000 с пределом 3 каждого типа дало бы 1180 при (3,3,3), а не 320. Это расхождение исходных единиц, не ошибка решателя; буквальное B=4000 превышает документированный предел приложения.
- В общей инструкции методички следующие столбцы F предлагается получать линейным умножением. Это противоречит нелинейным таблицам примера и вариантов 1, 2, 5. Приложение сохраняет именно полные табличные ценности, что подтверждено контрольными расчётами.

## Повторение проверки

Из `knapsack-practicum` с рабочим Tk и графической сессией:

```bash
python -B -m unittest discover -v
python -B app.py --smoke-test
```

Только новые сценарии: `python -B -m unittest test_acceptance -v`. Только ядро: `python -B -m unittest test_solver test_lesson test_formats test_presets -v`. Для сохранения протоколов задать переменную окружения `LAB3_QA_OUTPUT` с целевой папкой. Тесты временно используют системный буфер обмена.

На использованном macOS-хосте GUI запускается `/opt/homebrew/bin/python3.14`; Python 3.12 установлен без Tk. Сценарий [capture.py](capture.py) и [native_snapshot.py](native_snapshot.py) повторяют снимки только на macOS.

Windows EXE не собирался и не запускался; workflow проверен по конфигурации, но не исполнялся в этом прогоне. Также не выполнялось динамическое сравнение с исходным Windows EXE. Проверка его поведения в предыдущем исследовании была статической. Перед передачей Windows-сборки нужны запуск workflow и проверка полученного EXE на Windows.
